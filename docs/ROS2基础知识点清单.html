PART 1

环境与工具

这一部分决定「命令能不能跑起来」，90% 的新手问题都在这里。
1.1

source：每个新终端都要做一次

ROS 2 的可执行文件、环境变量都挂在 /opt/ros/humble 下，新终端默认不认识 ros2 命令，必须先 source。

$ ros2
ros2: command not found
$ source /opt/ros/humble/setup.bash
$ ros2 topic list
/parameter_events
/rosout
  • source 只对当前终端有效，开新终端要再做一次。
  • 顺序：先 source 系统 /opt/ros/humble，再 source 自己工作空间的 install/setup.bash。
  • 同名包，后 source 的覆盖先 source 的。
  • 写进 ~/.bashrc 可自动执行；但不要把两个发行版都写进去。
1.2

ROS_DOMAIN_ID：别和别人串话题

ROS 2 默认自动发现同一局域网里所有电脑的节点。全实验室都用默认的 0 时，别人发的 /cmd_vel 你的底盘也会收到——这就是「车自己在乱跑」的经典原因。

export ROS_DOMAIN_ID=17       # 每人一个，0 ~ 101
export ROS_LOCALHOST_ONLY=1   # 自己练习：只在本机通信
  • 车上的电脑也设一个固定 DOMAIN_ID，调车时不串。
  • source、export 都写进 ~/.bashrc，新终端自动生效。
  • Jazzy 起推荐用 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST 代替 LOCALHOST_ONLY。
1.3

工作空间与功能包

工作空间就是一个文件夹，标准结构只有 src/ 是你写的，其余三个由 colcon 生成。

目录 / 文件是什么要点
src/源码只有它进 git；真实比赛工程里常有十几个包
build/编译中间文件可随时删除重编
install/编译结果source 的是它，不是 src
log/编译日志编译失败先翻这里
package.xml包名、依赖决定 colcon 的编译顺序
CMakeLists.txt怎么编译可执行文件、安装规则都写这里
cd ~/mini_sentry_ws/src
ros2 pkg create my_pkg \
  --build-type ament_cmake \
  --dependencies rclcpp geometry_msgs
不要

把 build/ install/ log/ 提交到 git：它们能随时重新生成，提交了只会天天冲突。

1.4

colcon build：改代码 → 编译 → source → 运行

这个顺序是本课出现频率最高的一条操作习惯。少做一步，症状各不相同。

命令（在工作空间根目录执行）作用
colcon build编译所有包
colcon build --packages-select mini_sentry只编一个包，改一个包时最常用
colcon build --symlink-install软链接安装：改 launch / yaml 不用重编
source install/setup.bash让当前终端找到新编出来的包
rm -rf build install log彻底重来（编译状态莫名其妙坏掉时）

编译顺序不用自己排：colcon 读 package.xml 的依赖，先编 interfaces 再编用到它的包。编译完要在当前终端重新 source 一次，否则新包不可见。

易错

新终端报 Package 'mini_sentry' not found：不是包没编，是这个终端没 source。

1.5

改了什么需要重新 build

用 --symlink-install 后，配置文件改动可以直接生效，但代码和构建规则不行。

改动普通 buildsymlink-install
.cpp / .hpp 代码要要
launch .py / yaml / rviz要不用
新增文件、改 CMakeLists要要
PART 2

节点与通信

本课最重的一块：三种通信方式 + 一个最容易被忽视的 QoS。
2.1

节点、话题、消息的三句话定义

  • 节点：只负责一件事的程序。节点之间不直接调函数，只交换消息。
  • 话题：名字 + 类型。/cmd_vel 靠名字对上号，两边消息类型必须一致。
  • 话题通信：单向、多对多，发完就走，不管谁在听。适合持续的数据流：图像、点云、速度。
常用消息含义典型话题
sensor_msgs/Image图像/image_raw
sensor_msgs/PointCloud2点云/livox/lidar
sensor_msgs/Imu姿态、角速度、加速度/livox/imu
geometry_msgs/Twist速度指令/cmd_vel
nav_msgs/Odometry里程计位姿 + 速度/odom
关键

带 header 的消息里，stamp 是采集时刻，frame_id 是在哪个坐标系里测的。这两个字段后面 TF 全靠它们，不要随手填 now() 或空。

2.2

写一个发布者：往 /cmd_vel 发速度

四件事：继承 rclcpp::Node、构造函数里起节点名、建发布者、用定时器周期发。

class CmdTest : public rclcpp::Node {
public:
  CmdTest() : Node("cmd_test") {                  // 节点名
    pub_ = create_publisher<Twist>("cmd_vel", 10);  // 话题名、队列深度
    timer_ = create_wall_timer(100ms, [this]() {  // 每 100 ms
      Twist cmd;
      cmd.linear.x  = 0.5;   // 前进 0.5 m/s
      cmd.angular.z = 0.5;   // 逆时针 0.5 rad/s
      pub_->publish(cmd);
    });
  }
};
  • rclcpp::spin(node)：等事件、调回调，直到 Ctrl+C；末尾 rclcpp::shutdown()。
  • 打日志用 RCLCPP_INFO，自动带节点名和时间戳。
  • 不写代码也能发：ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.5}, angular: {z: 0.5}}"。
  • 单位统一国际单位：米、秒、弧度；linear.x 向前 m/s，angular.z 逆时针 rad/s。
2.3

新加一个节点，要改三个地方

漏掉任何一处，症状都不一样——这是「编译过了却跑不起来」的主要来源。

# ① package.xml：声明依赖
<depend>rclcpp</depend>
<depend>geometry_msgs</depend>

# ② ③ CMakeLists.txt
find_package(rclcpp REQUIRED)
find_package(geometry_msgs REQUIRED)

add_executable(cmd_test src/cmd_test.cpp)               # ② 编译
target_link_libraries(cmd_test rclcpp::rclcpp ${geometry_msgs_TARGETS})

install(TARGETS cmd_test DESTINATION lib/${PROJECT_NAME}) # ③ 安装
漏了哪步现象
① 依赖colcon 排不对编译顺序，时好时坏地报「找不到接口包」
② 编译根本没生成可执行文件
③ 安装编译成功，ros2 run 却报 No executable found

多用一个包（sensor_msgs、cv_bridge、自己的接口包…），就要同时加 depend、find_package、target_link_libraries。老教程的 ament_target_dependencies() 从 Kilted 起已弃用，target_link_libraries 在 Humble～Lyrical 都能用。

2.4

写一个订阅者：底盘仿真

cmd_sub_ = create_subscription<geometry_msgs::msg::Twist>(
  "cmd_vel", 10,
  [this](geometry_msgs::msg::Twist::SharedPtr msg) {
    cmd_ = *msg;                 // 回调里只保存
    last_cmd_time_ = now();
  });
odom_pub_ = create_publisher<nav_msgs::msg::Odometry>("odom", 10);
timer_ = create_wall_timer(20ms, [this]() { update(); }); // 50 Hz
  • 签名：create_subscription<类型>(话题名, 深度, 回调)；每来一条消息，spin 调一次回调。
  • 回调里只保存最新指令，真正的积分放在固定频率定时器里做——这决定了控制频率稳定。
  • 同一个节点可以既订阅又发布（这里收 /cmd_vel、发 /odom）。
  • 积分公式：x += (vx·cosψ − vy·sinψ)·dt，y += (vx·sinψ + vy·cosψ)·dt，ψ += wz·dt。
推荐

超时停车：超过 0.5 s 没收到速度指令就把 vx、vy、wz 清零。上游导航崩了，车也不会一直往前冲。

禁止

默认单线程：一个回调没返回，其它回调全在排队。回调里不要 sleep、不要死循环、不要同步等别人回复。

2.5

收图像：自瞄节点的入口

img_sub_ = create_subscription<Image>(
  "image_raw", rclcpp::SensorDataQoS(),
  [this](Image::ConstSharedPtr msg) {
    cv::Mat img = cv_bridge::toCvShare(msg, "bgr8")->image; // 不拷贝像素
    Armors out = detect(img);
    out.header = msg->header;   // 时间戳、frame_id 原样带下去
    armors_pub_->publish(out);
  });
  • 图像就是一个普通话题：相机驱动发布，识别节点订阅。
  • cv_bridge 负责 ROS 的 Image ↔ OpenCV 的 cv::Mat 互转。
  • 结果必须带上图像的 header：之后查 TF 要的是「拍这张图那一刻」的云台姿态。
  • 依赖：package.xml 加 cv_bridge、sensor_msgs；CMake 加 find_package(cv_bridge) 并链接 cv_bridge::cv_bridge。
易错

识别比相机慢时，旧图会在队列里排队。宁可丢帧也别处理过时的图：SensorDataQoS().keep_last(1)。

2.6

回调与执行器：一个回调卡住，整个节点都卡住

spin 背后是执行器。默认只有一个线程，回调一个一个排队执行：图像回调每帧 28 ms，定时器每 10 ms 就该跑一次——单线程下定时器会在队列里等（讲义里画的「红线」就是这个现象）。

auto img_group   = create_callback_group(CallbackGroupType::MutuallyExclusive);
auto timer_group = create_callback_group(CallbackGroupType::MutuallyExclusive);

SubscriptionOptions opt;
opt.callback_group = img_group;
img_sub_ = create_subscription<Image>("image_raw", SensorDataQoS(), cb, opt);
timer_   = create_wall_timer(10ms, on_timer, timer_group);

// main() 换成多线程执行器
rclcpp::executors::MultiThreadedExecutor exec;
exec.add_node(node);
exec.spin();
  • 同一个回调组里的回调不会同时跑；不同组 + 多线程执行器才能并行。
  • 并行之后，两个回调读写的同一个变量要用 std::mutex 保护。
  • 判断原则：回调都很快时，默认单线程就够用，别为了「显得高级」上多线程。
2.7

命令行看话题：list → hz → echo → info

$ ros2 topic list          # 有没有这个话题
$ ros2 topic hz /odom      # 频率对不对
average rate: 50.003
  min: 0.019s max: 0.021s std dev: 0.00041s
$ ros2 topic info /cmd_vel
Type: geometry_msgs/msg/Twist
Publisher count: 1
Subscription count: 1
$ ros2 topic echo /odom --once   # 数值对不对

这个顺序就是排查数据链路的固定动作：有没有 → 频率对不对 → 数值对不对。

2.8

自定义消息：把裁判系统数据搬进 ROS

# mini_sentry_interfaces/msg/GameStatus.msg
uint8 PROGRESS_NOT_STARTED=0   # 常量全大写
uint8 PROGRESS_RUNNING=4

uint8  game_progress
uint16 stage_remain_time       # 秒
uint16 current_hp
uint16 maximum_hp
find_package(rosidl_default_generators REQUIRED)
rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/GameStatus.msg" "srv/SetMode.srv" "action/GoToPoint.action")
ament_export_dependencies(rosidl_default_runtime)
package.xml 要加的什么时候需要
<buildtool_depend>rosidl_default_generators固定要加
<exec_depend>rosidl_default_runtime固定要加
<member_of_group>rosidl_interface_packages固定要加
<depend>action_msgs只有 .action 文件时才加
  • 命名规则：文件名大驼峰 GameStatus.msg → 头文件 game_status.hpp；字段小写 + 下划线；常量全大写。不符合直接编译报错。
  • 接口单独放一个包：识别、决策、可视化都依赖它，互相之间不会循环依赖。
  • 发送方和接收方按字段名读写，不用关心字节怎么排。
2.9

QoS：明明有数据，为什么收不到

相机驱动按传感器惯例用 SensorDataQoS 发布（BEST_EFFORT），你写订阅时只写了个数字 10（RELIABLE）。hz 显示 100 Hz，你的回调却一次都没进，启动日志里还有一句 WARN：

[WARN] [detector]: New publisher discovered on topic '/image_raw',
offering incompatible QoS. No messages will be received from it.
Last incompatible policy: RELIABILITY
写法可靠性队列深度
只写数字 10RELIABLE10
SensorDataQoS()BEST_EFFORT5
发布者提供订阅者要求能连上？
RELIABLERELIABLE能
RELIABLEBEST_EFFORT能
BEST_EFFORTBEST_EFFORT能
BEST_EFFORTRELIABLE不能
记住

订阅者的要求不能高于发布者。订阅传感器数据就用 SensorDataQoS()；查发布者实际用的 QoS 用 ros2 topic info -v。命令行工具用兼容性更宽的 QoS，所以 hz 能收到不代表你的节点能收到。

RViz2 里点云、图像不显示，先找 Reliability 改成 Best Effort。

2.10

QoS 持久性：后启动的节点能不能拿到之前的消息

static_transform_publisher 只在启动时发一次 /tf_static，10 分钟后才打开 RViz2 却还能看到——因为它用 TRANSIENT_LOCAL 发布：DDS 替后来的订阅者留着最近几条。

auto qos = rclcpp::QoS(1).transient_local();
pub_ = create_publisher<OccupancyGrid>("map", qos);
sub_ = create_subscription<OccupancyGrid>("map", qos, cb); // 订阅端也要写
策略取值怎么选
可靠性RELIABLE / BEST_EFFORT传感器流用 BEST_EFFORT；指令、结果用 RELIABLE
历史深度KEEP_LAST(n)只要最新写 1；怕丢就大一些
持久性VOLATILE / TRANSIENT_LOCAL只发一次的数据（地图、机器人描述、静态 TF）用 TRANSIENT_LOCAL
易错

持久性也要兼容：发布者 VOLATILE、订阅者要求 TRANSIENT_LOCAL，同样连不上。订阅端忘了写 qos，就只能收到之后发的消息。

2.11

服务：一问一答

很快能做完、需要知道成功没有的事：切换模式、保存地图、清空代价地图。

# SetMode.srv：--- 上面是请求，下面是响应
uint8 mode
---
bool   success
string message

$ ros2 service call /set_mode mini_sentry_interfaces/srv/SetMode "{mode: 1}"
response:
  success=True, message='已切换到 待命'
  • 服务端 create_service<SetMode>(名字, 回调(req, res))：拿到请求、填好响应，return 就算回复了。
  • .srv 里的常量（PATROL、HOLD、RETREAT）生成在 SetMode::Request 里。
  • 服务端回调要快；要跑好几秒的事用动作。
2.12

服务客户端：异步发，别在回调里干等

client_ = create_client<SetMode>("set_mode");
if (!client_->service_is_ready()) return;   // 服务端可能还没起来

auto req = std::make_shared<SetMode::Request>();
req->mode = SetMode::Request::HOLD;
client_->async_send_request(req, [this](rclcpp::Client<SetMode>::SharedFuture f) {
  RCLCPP_INFO(get_logger(), "%s", f.get()->message.c_str());
});
禁止

不要在定时器或订阅回调里 async_send_request 之后马上 .get() 或 spin_until_future_complete：单线程执行器腾不出手处理响应，节点直接卡死。

正确做法就是上面这样：给 async_send_request 传一个回调，响应到了执行器再调用它。

2.13

动作：耗时任务，有进度、可取消

# GoToPoint.action：目标 / 结果 / 反馈
float64 x
float64 y
---
bool    reached
float64 total_time
---
float64 distance_remaining

$ ros2 action send_goal /go_to_point mini_sentry_interfaces/action/GoToPoint \
    "{x: 3.0, y: 2.0}" --feedback
Feedback: distance_remaining: 3.5355
Goal finished with status: SUCCEEDED

客户端三件套：async_send_goal(goal, opts) 发目标 → feedback_callback 持续收进度 → result_callback 收结果（SUCCEEDED / ABORTED / CANCELED）。

  • 发之前判断 client_->action_server_is_ready()。
  • 半路改主意：client_->async_cancel_all_goals()，再发新目标（血量低要撤退就是这个场景）。
  • 依赖 rclcpp_action，package.xml 和 CMake 都要加。
  • Nav2 对外就是一个动作 /navigate_to_pose，把类型换成 nav2_msgs::action::NavigateToPose、目标换成 PoseStamped，写法完全一样。
PART 3

参数与 launch

赛场上不改代码就能调；以及一条命令把整车拉起来。
3.1

参数：名字 + 默认值

max_speed_ = declare_parameter("max_speed", 2.0);  // 返回当前值
# mini_sentry/config/sentry.yaml
chassis_sim:              # 第一层：节点名
  ros__parameters:        # 固定写法，两个下划线
    max_speed: 2.0
    rate: 50.0
sentry_brain:
  ros__parameters:
    retreat_hp: 150
  • 加载方式一：ros2 run mini_sentry chassis_sim --ros-args --params-file sentry.yaml。
  • 加载方式二：命令行直接给，-p max_speed:=1.0。
  • 加载方式三：launch 里 parameters=[yaml 路径]，比赛里最常用这个。
  • 查看与修改：ros2 param list / get / set。
3.2

为什么 param set 成功了，车还是按老速度跑

节点只在构造函数里读了一次参数、存进成员变量 max_speed_，之后不会跟着变。想在线调，必须注册参数回调。

OnSetParametersCallbackHandle::SharedPtr param_cb_;  // 句柄一销毁，回调就失效

param_cb_ = add_on_set_parameters_callback(
  [this](const std::vector<rclcpp::Parameter> & ps) {
    rcl_interfaces::msg::SetParametersResult r;
    r.successful = true;
    for (const auto & p : ps) {
      if (p.get_name() != "max_speed") continue;
      if (p.as_double() <= 0.0) {          // 不合理的值可以拒绝
        r.successful = false;
        r.reason = "max_speed 必须大于 0";
      } else {
        max_speed_ = p.as_double();
      }
    }
    return r;
  });
yaml 的坑症状
声明成 double，yaml 里写 2报类型错误，必须写 2.0
第一层节点名写错参数不生效，而且不报错——最难查的一类
推荐

图形界面调参：ros2 run rqt_reconfigure rqt_reconfigure，选节点直接改数。调好了一定要 ros2 param dump /chassis_sim > tuned.yaml 存回去，否则重启就没了。

3.3

launch：一条命令启动一整套

def generate_launch_description():
    pkg = get_package_share_directory('mini_sentry')
    params = os.path.join(pkg, 'config', 'sentry.yaml')
    return LaunchDescription([
        Node(package='mini_sentry', executable='chassis_sim', parameters=[params]),
        Node(package='mini_sentry', executable='sentry_brain',
             parameters=[params], output='screen'),
        Node(package='tf2_ros', executable='static_transform_publisher',
             arguments=['--x', '0.2', '--y', '0.1', '--z', '0.4', '--yaw', '1.5708',
                        '--frame-id', 'base_link', '--child-frame-id', 'livox_frame']),
    ])
launch 里的常用参数作用
parameters=[params]加载 yaml 参数
output='screen'日志打在这个终端里，方便看红字
remappings=[('cmd_vel','cmd_vel_nav')]话题改名，接别人的包不用改他的代码
respawn=True, respawn_delay=1.0崩了 1 s 自动拉起，比赛中不用人去重启
IncludeLaunchDescription(...)嵌套别人的 launch，一份总 launch 套相机、识别、导航
parameters=[{'use_sim_time': True}]跑仿真、回放 bag 时必须开，否则时间对不上
易错

launch、yaml、rviz 文件要在 CMakeLists 里 install(DIRECTORY …)，否则 get_package_share_directory 找不到，launch 直接报错。

3.4

组件：相机和识别放进一个进程，图像不用拷贝

  • 普通节点：两个进程，图像要序列化 → 走 DDS → 反序列化。1280×1024×3 每帧拷贝约 3.9 MB。
  • 组件：编译成动态库的节点，由容器进程加载；同一个容器内开了进程内通信，消息直接传指针。
  • 自瞄常把相机、识别、跟踪放进一个容器。
// 节点写成组件：构造函数收 NodeOptions，不写 main
class Detector : public rclcpp::Node {
public:
  explicit Detector(const rclcpp::NodeOptions & options)
  : Node("detector", options) {}
};
#include "rclcpp_components/register_node_macro.hpp"
RCLCPP_COMPONENTS_REGISTER_NODE(Detector)

// launch：放进同一个容器
ipc = [{'use_intra_process_comms': True}]
ComposableNodeContainer(
    name='vision', package='rclcpp_components', executable='component_container',
    composable_node_descriptions=[
        ComposableNode(package='camera',   plugin='CameraNode', extra_arguments=ipc),
        ComposableNode(package='detector', plugin='Detector',   extra_arguments=ipc),
    ])
注意

真正零拷贝还要求发布时用 std::unique_ptr：pub_->publish(std::move(msg))。代价是：一个组件崩了，整个容器都会退出。

PART 4

TF 坐标变换

自瞄和导航都绕不开：每个传感器在自己的坐标系里说话。
4.1

TF 是什么：车上的坐标系树

每个传感器都在自己的坐标系里测量：点云在 livox_frame，装甲板在 camera_link。TF（tf2）记录所有坐标系之间的相对位置，帮你把点、位姿从一个坐标系换算到另一个。

导航要把点云换到 map 里规划；自瞄要把装甲板换到 odom 里，不跟着云台转，才好做跟踪预测。

map
 └── odom                    # 重定位发布，修正漂移
      └── base_link          # 里程计发布（LIO / 轮速计）
           ├── livox_frame   # 静态：雷达安装位置
           ├── gimbal_yaw    # 动态：跟着云台角度实时发布
           │    └── gimbal_pitch
           │         └── camera_link   # 静态：相机安装位置
           └── …
约定

REP 103：x 前、y 左、z 上；单位米、弧度，逆时针为正。每个坐标系只有一个父节点，每条边只有一个发布者。

步兵自瞄有个更简单的画法：odom → gimbal_link（按云台 IMU 姿态实时发）→ camera。相机光学坐标系是 z 朝前、x 朝右、y 朝下，所以通常再挂一个 camera_optical_frame。

4.2

map 与 odom：为什么要两层

odommap
连续性连续，不会跳定位修正时会跳一下
长期精度越跑越漂不漂
谁发里程计（轮速计、LIO）重定位
拿来做控制、短时跟踪预测全局目标点、规划
关键

定位节点发的是 map → odom，不是 map → base_link：odom → base_link 已经有人发了，每条边只能有一个发布者。

只做自瞄、不导航的车，通常只有 odom 这一层。自瞄跟踪一定要用 odom：目标位置不能因为定位修正跳一下就乱掉。规范见 REP 105。

4.3

发布静态 TF：传感器装在哪

ros2 run tf2_ros static_transform_publisher \
  --x 0.2 --y 0.1 --z 0.4 --yaw 1.5708 \
  --frame-id base_link \
  --child-frame-id livox_frame
  • 平移单位米，角度单位弧度；1.5708 rad = 90°。launch 里写法相同。
  • 外参量错 1°，10 m 外的点就偏 10 × tan1° ≈ 0.17 m；雷达倾斜安装时 roll、pitch 也要量准。
  • 雷达、相机、云台多了，可以写进 URDF，由 robot_state_publisher 统一发布。
4.4

发布动态 TF：随时间变的位姿

tf_broadcaster_ = std::make_unique<tf2_ros::TransformBroadcaster>(*this);

tf2::Quaternion q;
q.setRPY(0, 0, yaw_);                  // 欧拉角 → 四元数，别手算
geometry_msgs::msg::TransformStamped tf;
tf.header.stamp    = t;                // 这个位姿对应的时刻
tf.header.frame_id = "odom";         // 父
tf.child_frame_id  = "base_link";     // 子
tf.transform.translation.x = x_;
tf.transform.translation.y = y_;
tf.transform.rotation.z    = q.z();
tf_broadcaster_->sendTransform(tf);
禁止

一条边只能一个人发。LIO 和仿真都发 odom → base_link，TF 会来回跳，RViz2 里车会闪。云台的 TF 同理：每收到一次新的云台角度就发一次。

4.5

查询 TF：把点换到另一个坐标系

tf_buffer_   = std::make_unique<tf2_ros::Buffer>(get_clock());
tf_listener_ = std::make_shared<tf2_ros::TransformListener>(*tf_buffer_);

geometry_msgs::msg::PointStamped p;
p.header.frame_id = "livox_frame";
p.header.stamp    = rclcpp::Time(0);   // 0 = 用最新的变换
p.point.x = 2.0;
try {
  auto in_base = tf_buffer_->transform(p, "base_link");
  auto in_odom = tf_buffer_->transform(p, "odom");
} catch (const tf2::TransformException & ex) {
  RCLCPP_WARN(get_logger(), "%s", ex.what());
}
  • Buffer 记住最近一段时间的所有 TF，可以查任意两个坐标系的关系，中间隔几层都行。
  • 查询一定会失败（还没收到、树断了），所以必须 try / catch。
  • 讲义示例：车在 (3, 1)、车头朝 +x 时，雷达说「x 方向 2 m」（雷达侧装、x 朝车的左边），对底盘是左边 2.1 m，对场地是 (3.2, 3.1)。
4.6

按时间查 TF：拍照那一刻，云台在哪

识别一帧要十几毫秒，这期间云台一直在转。用「现在」的 TF 去换算，等于用错姿态。必须用图像的时间戳查，Buffer 会在前后两条 TF 之间插值。

auto tf = tf_buffer_->lookupTransform(
    "odom", msg->header.frame_id,          // 目标系、源系
    msg->header.stamp,                     // 拍照那一刻
    rclcpp::Duration::from_seconds(0.02)); // 最多等 20 ms

geometry_msgs::msg::PoseStamped in_odom;
tf2::doTransform(armor_in_cam, in_odom, tf);
  • 时间戳 0 = 用最新变换；自瞄用图像时间戳。
  • Buffer 默认只存最近 10 s 的 TF，太老的时间戳也查不到。
  • t₀ 比最新 TF 还新 → extrapolation into the future，要么给等待时间，要么检查发 TF 的节点。
  • 等待会占住回调；不想阻塞就用 tf2_ros::MessageFilter：TF 到齐了才把图像交给回调。
  • 前提是云台 TF 的时间戳打得准：用收到这帧云台数据的时刻，不是随手写 now() 或 0。
4.7

TF 出问题：先看树，再看数

工具 / 报错原因怎么查
ros2 run tf2_tools view_frames生成 frames.pdf，看树是否完整、每段谁发、多少 Hz看树
ros2 run tf2_ros tf2_echo base_link livox_frame打印两坐标系的平移与 RPY，核对外参看数
not part of the same tree树断了：某段没人发，比如重定位没启动，缺 map → odomview_frames
